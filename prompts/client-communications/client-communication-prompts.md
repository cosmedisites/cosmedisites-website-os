# Client Communication Prompts

## C01 — Kick-Off Email

**Use when:** After project onboarding.  
**Inputs:** Relevant project artefacts / tracker.  
**Produces:** Client-facing communication.

```text
Draft the CosmediSites project kick-off email.

Inputs:
- client name;
- project scope;
- project lead;
- first milestone;
- discovery / input requirements;
- meeting link/date if supplied.

Include:
1. Welcome and one-sentence project objective.
2. What happens first.
3. What we need from the client before discovery.
4. Who their main contact is.
5. Immediate next date/action.

Tone: warm, organised, concise.
Do not overwhelm the client with the full internal SOP.
Do not promise launch dates unless confirmed.
```

## C02 — Discovery Input Request

**Use when:** Before discovery.  
**Inputs:** Relevant project artefacts / tracker.  
**Produces:** Client-facing communication.

```text
Draft the client’s pre-discovery information request.

Ask only for information not already supplied, prioritising:
- service/treatment list;
- practitioner/team details;
- locations;
- booking process;
- main revenue/growth priorities;
- brand assets;
- analytics/search access if in scope;
- current photography/results/reviews;
- known compliance constraints.

Make clear that incomplete information can be discussed on the call.
Do not send a 40-question questionnaire unless the project genuinely requires it.
```

## C03 — Strategy Review Invitation

**Use when:** When the client strategy deck is ready.  
**Inputs:** Relevant project artefacts / tracker.  
**Produces:** Client-facing communication.

```text
Draft the invitation to the website strategy/design review.

Explain that the meeting is to agree:
- overall positioning;
- patient journey;
- site structure where relevant;
- visual direction;
- practitioner/clinic hierarchy;
- photography direction.

Tell the client they do not need to prepare design ideas.
Their job is to confirm accuracy, business fit and whether the proposed direction represents where the clinic is going.

Include the deck/link if supplied and meeting logistics.
```

## C04 — Strategy Review Follow-Up

**Use when:** Immediately after the review.  
**Inputs:** Relevant project artefacts / tracker.  
**Produces:** Client-facing communication.

```text
Using the Approval Record, draft a client follow-up.

Structure:
- what we agreed;
- what we are changing;
- what remains open;
- what we need from you;
- what happens next.

State approved decisions clearly.
Ask for explicit responses only on unresolved items.
Avoid “let us know any thoughts”.
```

## C05 — Content / Photography Request

**Use when:** After strategy approval.  
**Inputs:** Relevant project artefacts / tracker.  
**Produces:** Client-facing communication.

```text
Turn the Content/Input Tracker and Photography Brief into a client-friendly request.

Group:
NEEDED NOW
NEEDED BEFORE LAUNCH
OPTIONAL / CAN FOLLOW

For each item make the expected format clear.
For photography include the shoot list at a sensible level without exposing internal component jargon.
If patient content requires consent, state that clearly.
```

## C06 — Revision Summary

**Use when:** When sending a revised design/deck.  
**Inputs:** Relevant project artefacts / tracker.  
**Produces:** Client-facing communication.

```text
Draft the revision summary for the client.

Include:
- feedback received;
- changes made;
- anything deliberately unchanged and why, in calm client language;
- decisions now ready for approval;
- any new facts that changed the strategy.

Do not defend the team emotionally.
Do not imply every preference was implemented if doing so would contradict an approved direction.
```

## C07 — Pre-Launch Approval Request

**Use when:** When the launch candidate is ready.  
**Inputs:** Relevant project artefacts / tracker.  
**Produces:** Client-facing communication.

```text
Draft the client pre-launch approval message.

Confirm:
- what is ready;
- what the client is being asked to verify (accuracy, practitioner details, contact/booking, pricing, etc.);
- what CosmediSites has separately QA’d;
- outstanding non-blocking items if any;
- deadline for approval if supplied.

Do not ask the client to perform technical QA.
Ask them to validate the things only they can authoritatively confirm.
```

## C08 — Launch Notification

**Use when:** After launch checks pass.  
**Inputs:** Relevant project artefacts / tracker.  
**Produces:** Client-facing communication.

```text
Draft the launch notification.

Include:
- the site is live;
- core checks completed;
- any known non-blocking item being monitored;
- what not to change immediately if a migration/measurement period is underway;
- support route;
- date/expectation for the first post-launch review.

Do not claim performance improvement before sufficient data exists.
```

## C09 — 30/60/90 Review Summary

**Use when:** After a post-launch review.  
**Inputs:** Relevant project artefacts / tracker.  
**Produces:** Client-facing communication.

```text
Turn the internal post-launch review into a concise client update.

Structure:
WHAT WE’RE SEEING
WHAT IS WORKING
WHAT WE’RE IMPROVING
WHAT WE WANT TO TEST
WHAT WE NEED FROM YOU, if anything

Clearly distinguish measured facts from hypotheses.
Do not flood the client with vanity metrics.
Lead with bookings/leads/commercially relevant behaviour where tracked.
```
