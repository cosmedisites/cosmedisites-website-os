# CosmediSites Website Redesign SOP v1.0

## Purpose

Use this SOP for every strategic website redesign project.

The objective is:

**commercial brief → evidence → strategy → approved direction → build → launch → measured outcome**

The Website Strategy Playbook explains the methodology. This SOP controls execution.

## Core rule

> **Architecture follows business strategy.**

Do not begin visual design until the business direction, positioning and site architecture are understood.

---

# Project roles

| Role | Primary responsibility |
|---|---|
| Project Lead | Delivery, timeline, client communication and gates |
| Strategist | Commercial brief, evidence, positioning, UX and architecture |
| SEO Lead | Search architecture, migrations, internal linking and search preservation |
| Creative Lead | Accountable for visual/brand quality; may be fulfilled by the senior designer or Project Lead on smaller projects |
| Designer | Visual system, UX execution, components and responsive design |
| Developer | Build and technical implementation |
| Content Lead | Copy, content production and input management |
| Compliance Reviewer | Claims, practitioner details, treatment wording, proof |
| Independent QA Reviewer | Final strategy/UX quality check |

One person may hold multiple roles on smaller projects.

Every stage still has **one named owner**.

---

# Decision hierarchy

1. **Business strategy**
2. **Positioning**
3. **UX / information architecture**
4. **Content / proof**
5. **Visual expression**

Lower-level preference should not casually overturn a higher-level decision.

# Stage 0 — Project Strategy Brief

**Owner:** Project Lead / Strategist  
**Client involved:** Yes  
**Output:** Project Strategy Brief  
**Approval:** Client confirms factual accuracy

## Capture

- Why the client hired CosmediSites
- Commercial objective
- Locations now / planned
- Current practitioners / planned team
- Core revenue services
- Services to grow
- Target patient/customer
- Current lead sources
- Booking process
- Website role in acquisition
- Known SEO priorities
- Known brand problems
- Compliance/regulatory constraints
- Technical/CMS constraints
- Deadline/scope constraints

## Definition of Done

- [ ] Business objective is explicit.
- [ ] Growth model and priority services are understood.
- [ ] Audience and buying anxieties are documented.
- [ ] Website role in acquisition is clear.
- [ ] Known SEO/compliance constraints are captured.
- [ ] Client confirms the factual brief.

The team can answer:

> What does this business need the new website to achieve?

And:

> What would make the redesign commercially unsuccessful even if it looked excellent?

# Stage 1 — Evidence Pack

**Owner:** Strategist  
**Reviewer:** Project Lead  
**Client involved:** No  
**Output:** Evidence Pack

## Review

- Current website
- Mobile
- Analytics/Search Console where available
- Google Business Profile where relevant
- Existing photography
- Brand consistency
- Treatments/services
- Practitioners
- Results/reviews
- Booking journey
- Competitors

## Classify

**KEEP / CHANGE / MISSING / UNCERTAIN**

## Definition of Done

- [ ] Website reviewed.
- [ ] Mobile reviewed.
- [ ] Competitors reviewed.
- [ ] Existing assets classified.
- [ ] Revenue-driving services identified.
- [ ] Growth priorities identified.
- [ ] Proof inventory started.
- [ ] Key unknowns identified.
- [ ] Strategic diagnosis drafted.

Required diagnostic sentence:

> "The existing site currently communicates X. The business needs to become Y. The primary barriers are A, B and C."

# Stage 2 — Strategic Diagnosis

**Owner:** Strategist  
**Reviewer:** Project Lead  
**Output:** Strategic Diagnosis

## Determine

- Current perception
- Desired perception
- Commercial weaknesses
- Trust weaknesses
- UX problems
- Brand architecture issues
- Scalability problems
- Priority opportunities

Do not prescribe visual styling yet.

## Definition of Done

- [ ] Diagnosis can be understood without discussing colours/fonts.
- [ ] Commercial, trust, UX and scalability issues are separated.
- [ ] Top three opportunities are prioritised.
- [ ] Every major conclusion traces back to evidence.

# Stage 3 — Positioning

**Owner:** Strategist  
**Reviewer:** Creative Lead / Project Lead  
**Client involved:** Strategic approval  
**Output:** Positioning Thesis

## Define

**Three-second perception**

> "Within three seconds of landing, the visitor should understand that this is..."

**Wrong perception**

> "It should never be mistaken for..."

Also define:

- Positioning thesis
- Priority services/categories
- What the clinic should be known for
- Clinic/practitioner brand architecture
- Future-growth implications

## Definition of Done

- [ ] Desired perception written.
- [ ] Wrong perception written.
- [ ] Positioning thesis agreed internally.
- [ ] Priority services/categories identified.
- [ ] Clinic/practitioner relationship defined.
- [ ] Future growth test passed.

No visual design begins until this is internally approved.

**Reviewer:** Project Lead

- Existing URLs to retain

- Pages to remove
- Redirect requirements
- Treatment/service hierarchy
- Concern hierarchy

- Practitioner structure
- Results/case architecture

- [ ] Existing high-value URLs have a retain/merge/redirect decision.
- [ ] Navigation model is defined.
- [ ] Internal linking is defined.
- [ ] Location/practitioner architecture is explicit.

# Stage 5 — Visual Direction

**Owner:** Designer  
**Reviewer:** Strategist / Creative Lead  
**Client involved:** Approval  
**Output:** Visual Direction / Style System

## Translate strategy into

- Colour
- Typography
- Spacing
- Photography language
- CTA hierarchy
- Card/container logic
- Iconography
- Motion
- Contrast
- Current → Proposed comparison

## Definition of Done

- [ ] Every major visual choice has a strategic rationale.
- [ ] System supports desktop and mobile.
- [ ] Photography direction is defined.
- [ ] CTA hierarchy is unambiguous.
- [ ] Client-facing explanation avoids internal design jargon.

## Designer handoff format

The strategist → designer handoff separates:

**LOCKED / FLEXIBLE / REQUIRED / AVOID / OPEN**

AVOID lists the patterns, signals and treatments the design must not use: wrong-category cues,
fabricated or placeholder proof presented as real, and styling that contradicts the positioning.

# Stage 7 — Proof + Content + Photography

**Owner:** Content Lead  
**Reviewer:** Strategist / Compliance Reviewer  
**Outputs:** Proof Inventory + Content/Input Tracker + Photography Brief

## Proof inventory

Track:

- Qualifications
- Registrations
- Memberships
- Awards
- Reviews
- Ratings
- Before/after cases
- Case information
- Media
- Teaching/speaking
- Expert content

No evidence is invented.

## Photography

Define:

- Practitioner portraits
- Consultations
- Clinic interiors
- Treatment preparation
- Treatment details
- Natural skin
- Before/after cases

AI imagery is allowed only as clearly labelled art-direction stand-ins.

Never fabricate:

- Practitioner portraits
- Before/after results
- Credentials
- Clinical evidence

## Definition of Done

- [ ] Proof gaps are known.
- [ ] Each missing input has an owner.
- [ ] Photography requirements are defined.
- [ ] Patient/model consent requirements are identified.
- [ ] Design does not depend on evidence nobody can supply.

# Stage 8 — Client Strategy Review

**Owner:** Project Lead  
**Presenter:** Strategist / Designer  
**Output:** Client Strategy Deck

Recommended story:

**Positioning → change → visual system → patient journey → distinctive ideas → page system → proof → mobile → photography → business outcome**

## Presentation rule

> **One sentence explains why. The visual proves it.**

Do not present several arbitrary directions when the team has enough evidence to recommend one.

## Definition of Done

- [ ] Deck tells a strategic story.
- [ ] Commercial outcome is explicit.
- [ ] Client approval items are explicit.
- [ ] Inputs/next steps are separated from approvals.

---

# Stage 9 — Approval Gate

**Owner:** Project Lead  
**Client involved:** Yes  
**Output:** Approval Record

Record explicit decisions for:

- Positioning
- Visual direction
- Navigation/user journey
- Service hierarchy
- Practitioner hierarchy
- Homepage structure
- Photography direction

Nothing enters full build until required strategic decisions are approved.

## Definition of Done

- [ ] Every strategic decision has a status.
- [ ] Feedback is classified before action.
- [ ] Locked decisions are identified.
- [ ] Client has a clear record of what happens next.

---

# Client Feedback Protocol

Classify all feedback before acting.

| Type | Example | Response |
|---|---|---|
| Strategic | "This does not reflect our move into dermatology." | Revisit strategy |
| Accuracy | "That is not Dr Smith's qualification." | Correct immediately |
| User / UX | "Patients will not understand this wording." | Investigate / resolve |
| Compliance | "We cannot make that claim." | Correct immediately |
| Preference | "I do not like serif fonts." | Assess against strategy |
| New information | "We are opening another location." | Assess which decisions genuinely change |

Not all feedback has equal strategic weight.

---

# Revision Control

**Round 1:** Strategic direction.

**Round 2:** Refinement against agreed strategic feedback.

Once a strategic decision has been explicitly approved, it becomes **locked**.

Reopen only when new:

- factual information
- commercial change
- user evidence
- technical limitation
- compliance requirement

materially changes the brief.

Personal preference alone does not automatically reopen previous stages.

**Reviewer:** Designer

# Stage 12 — Compliance + Strategy + Technical QA

Treat these as three separate checks.

## A. Compliance Review

**Owner:** Compliance Reviewer

Check:

- Claims
- Credentials
- Practitioner titles
- Treatment terminology
- Before/after presentation
- Testimonials
- Promotional language
- Pricing language
- Guarantees/outcome claims
- Patient consent

## B. Strategy / UX QA

**Owner:** Independent reviewer

Check:

- Positioning survives implementation
- Trust appears early enough
- User journeys work
- Clinic/practitioner hierarchy is correct
- CTAs are clear
- Mobile experience works
- Future scalability remains intact

## C. Technical / SEO QA

**Owner:** Developer + SEO Lead

Check:

- Indexability
- Metadata
- Canonicals
- Redirects
- Schema
- Internal links
- Performance
- Forms
- Tracking
- Responsive behaviour
- Broken links
- Consent/cookie implementation where applicable

## Definition of Done

- [ ] Compliance gate signed off.
- [ ] Strategy/UX gate signed off.
- [ ] Technical/SEO gate signed off.
- [ ] Blocking issues resolved or explicitly accepted.

# Stage 13 — Launch

**Owner:** Project Lead  
**Technical owner:** Developer  
**Output:** Launch Record + Measurement Baseline

Capture baseline data before/at launch where available:

- Traffic
- Leads
- Bookings
- Calls
- Key landing pages
- Relevant rankings
- Conversion rates
- Mobile behaviour
- GBP/search actions

Launch only after QA sign-off.

## Definition of Done

- [ ] Launch date and comparison period are recorded.
- [ ] Commercial conversion baseline exists where tracking permits.
- [ ] Priority search and landing-page baseline exists.
- [ ] Known tracking limitations are documented.

---

# Stage 14 — 30 / 60 / 90 Day Review

**Owner:** Strategist / Project Lead  
**Output:** 90-Day Redesign Performance Review

## 30 days — implementation

Check:

- Technical issues
- Forms/bookings
- Mobile behaviour
- Tracking
- UX friction
- Indexation/migration

## 60 days — behaviour

Review:

- CTA use
- Treatment-page engagement
- Navigation behaviour
- Search landing pages
- Content gaps
- Booking drop-off

## 90 days — business/search outcome

Assess:

- Leads/bookings trend
- Conversion behaviour
- Priority treatment performance
- Organic visibility
- Search performance
- Content opportunities
- Commercial lessons

Decide:

**KEEP → IMPROVE → TEST → SCALE**

Feed reusable learning back into the operating system.

## Definition of Done

- [ ] 30/60/90 reviews use the launch baseline.
- [ ] Actions are prioritised by commercial impact.
- [ ] At least one KEEP / IMPROVE / TEST / SCALE decision is recorded.
- [ ] Reusable learning is fed back into the playbook.
